# Fieldwork — Integrated Breach Builds 053–062

The playable tactical study remains `breach.html`. The older world and art
study are preserved as references, not dependencies.

## What changed in each staged build

| Build | Integrated foundation | Review target |
|---|---|---|
| 053 | Stable plan nodes, insert/delete/drag, visual nodes, undo/redo, touch modes | Change the middle of a plan without rewriting its generated route |
| 054 | One authoritative motor for planned traversal, smooth turning, occupancy checks, blocked doorway warnings | Reach expected stops without clipping and never silently discard a valid plan |
| 055 | Facing as a property of any waypoint; independent turning while moving | Cover one angle while continuing the approach |
| 056 | Explicit OPEN/KICK/HOLD door actions with staging positions, delay and noise | Closed doors stop movement and block sight until intentionally opened |
| 057 | Crouched posture, height-classified cover and exposure penalties | Crouching behind low cover matters without magically snapping positions |
| 058 | Target acquisition, ammunition/reloading, pressure/suppression, shot trails and minimal synthesized audio | Preparation changes the odds of a short firefight |
| 059 | Limited sight/hearing perception and investigating, engagement and cover states | Enemies react only to information available to them |
| 060 | Wait orders and a shared two-person synchronization code | Both soldiers wait until all living participants are ready |
| 061 | Explored terrain and last-known contact memory, kept separate from current vision | Contacts can be lost and are never revealed automatically |
| 062 | Secure records after clearing, then extract; debrief, casualties, shooting stats, and three authored arrangements | A complete, restartable mission instead of automatic win on the final kill |

## Execution model

- `breach-plan.ts` owns authored orders and undo history: stable plan-node
  identity cannot be confused with A* navigation vertices.
- `breach-core.ts` retains the original map, geometry, navigation, and
  Build 052 legacy kernel, used as a regression reference.
- `breach-game.ts` is the **only live simulation authority** for Breach's
  upgraded page. It runs in a fixed simulation timestep and owns movement,
  knowledge, action timings, perception, combat, objectives and outcome.
- `breach-main.ts` handles UI commands and rendering only. It observes the
  session; input callbacks do not move soldiers, damage enemies or open doors.
- Deterministic seeds permit reliable unit tests and repeatable encounter
  variants. Changing the arrangement requires a deliberate reset.

## Mobile touch controls

Tap a soldier or its roster button to select it. Tap the map to append a
destination. Drag directly from a soldier to draw, or drag an existing numbered
node to move it. Tap a node to select it. The top of the command ribbon gives
UNDO/REDO, + NODE (insertion between waypoints), and - NODE (delete selected).
LOOK then tap attaches an explicit facing to the chosen node.

For doors, choose the OPEN/KICK/HOLD method, press DOOR, and tap the actual
door. You can append a WAIT to the selected unit or SYNC to both. STAND/LOW
changes a unit's posture. SITE 1/3 cycles among three defender arrangements
with a fresh scenario. GO/PAUSE controls the shared clock.

Desktop: 1/2 select, SPACE GO/PAUSE, L look, X clear, R reset,
CTRL/CMD+Z undo and CTRL/CMD+SHIFT+Z redo.

## Important known scope limits

This is an **integrated first pass across ten systems**, not proof that each
one has reached final production quality. The cover model is geometric and
abstract, shooting uses a deterministic seeded hit model with visual traces
rather than raycast ballistic projectiles, enemy combat behavior is modest,
and coordinated commands are shared waits rather than an exhaustive
communication framework. Music, inventory, grenades, player loadouts,
campaign systems and procedural levels remain out of scope.

Each stage still needs a **real iPhone gameplay evaluation**, especially
route manipulation, narrow-door spacing, the readability of fog and feedback,
how long it takes guards to acquire targets, and whether extraction is fun.

Do not promote the prototype to the game's default page or merge until checks
and human inspection support it.
